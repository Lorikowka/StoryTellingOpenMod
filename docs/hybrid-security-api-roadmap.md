# Модульность Lua и безопасность сюжетных пакетов

Этот документ переносит в актуальную ветку направление из [`docs/hybrid-security-api-roadmap`](https://github.com/Lorikowka/StoryTellingOpenMod/tree/docs/hybrid-security-api-roadmap). Исходная ветка добавила только проектный раздел в `engine-expansion-plan.md`: нового API или изменений Java в ней нет. Ниже предложения сопоставлены с состоянием alpha.66. Полный порядок этапов остаётся в [основном плане](engine-expansion-plan.md).

## Авторский интерфейс

Обычные действия должны оставаться короткими: реплика, ожидание, движение NPC и выбор не требуют отдельной библиотеки или ручной передачи объекта `api`. Целевой синтаксис вроде `william:say("Привет")` и `player:think("...")` пока **не реализован**. Существующие `story`, `part`, `speaker`, `speech`, `think` и `npc{...}` сохраняются при разработке API 2.0.

Повторно используемые описания NPC уже можно возвращать из Lua-модуля, как в `characters/guide.lua`. Следующее поколение разделит неизменяемый шаблон, экземпляр в мире и постоянное состояние. Для каждого экземпляра нужен стабильный ключ и правило соответствия старым ключам в сохранениях. `Player` проектируется отдельно от NPC; постановочное управление игроком потребует явной очистки управления при отмене сцены.

## Граница доверия

Текущий `require` alpha.66 разрешает модуль только в `ST/scripts/`, отклоняет выход по пути или симлинку, ограничивает размер файла и число импортов, обнаруживает циклы и кэширует результат в пределах загрузки сценария. Это контроль файлового доступа, а не полная песочница. Lua-код пока выполняется при разборе на игровом потоке; для него нет гарантированных пределов времени и памяти. Модули разделяют окружение сценария, поэтому изоляции глобальных переменных между импортами пока нет.

Целевая модель: изоляция окружений модулей, явно выданные возможности для управления миром, игроком и инвентарём, проверка этих действий сервером и ограничение ресурсов исполнения. При установке пакета сведения об источнике и правах полезны пользователю, но не заменяют технических ограничений. Возможности отдельного JVM-процесса для недоверенных пакетов исследуются после фиксации контракта API.

## Пакеты и версии

Манифест будущего Story Pack должен задавать ID, версию пакета, совместимые версии движка и Lua API, зависимости, ресурсы и запрошенные возможности. Числовые Lua-файлы без манифеста остаются рабочим форматом прежнего API. Библиотеки проекта и сцены должны загружаться через контролируемый загрузчик. Конвертер имеет смысл после описания обеих версий API; он должен сообщать о несовместимостях, а не подменять произвольный Lua текстовыми заменами.

## Ближайшие проверки

1. Пройти `900051` в игре и проверить изменение библиотечного файла после `/script reload 900051.lua`.
2. Проверить одинаковые ограничения при начальной регистрации и выборочной перезагрузке сценария. Этот этап начат в ветке `fix/lua-module-boundaries`.
3. Расширить автоматические случаи: 64-й и 65-й импорт, размер на границе, кэш результатов `nil`/`false`, повтор после ошибки, длинное имя и симлинки. Ограничивать чтение файла до выделения большого массива памяти.
4. Описать модель угроз, формат пакета и права на игровые действия до установки сторонних сюжетных пакетов.
5. После контракта шага проектировать новый `StoryRuntime`: последовательное исполнение, сохранение, ожидание, отмена, ошибки; затем параллельные ветки и конфликтную политику для NPC и камеры.

Каждый шаг отмечается отдельно как проектный, проверенный сборкой или проверенный в Minecraft. Ветка с этим документом не объявляет API 2.0 готовым.
