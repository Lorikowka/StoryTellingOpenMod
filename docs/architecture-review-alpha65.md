# Разбор концепции Storytelling на alpha.65

Основа: пользовательский документ «Storytelling: архитектура, проблемы и план дальнейшего развития», сверенный с исходниками ветки `cleanup/script-command-categories` (`5ecc92d`). Это технический разбор текущей реализации, а не новая спецификация уже выпущенного API.

## Что уже есть

| Предложение документа | Состояние alpha.65 |
|---|---|
| Lua-сценарии вместо отдельного Java-класса на главу | `LuaStory` строит шаги сценария; пользовательские файлы лежат в `ST/scripts/`. Старые Java-сценарии пока присутствуют и инвентаризированы в `legacy-cleanup-audit.md`. |
| Объект NPC | `npc{key, model, name, width, height}` возвращает объект с `spawn`, `move`, `look`, `animate`, `use_block`, `remove`, `camera`, `speaker` и другими методами. Отдельных Template/Instance пока нет. |
| Портрет из группы Head | `NpcPortraits` ищет группу `Head` в glTF и растеризует портрет; при отсутствии группы использует стандартную иконку и пишет предупреждение. |
| Камера, диалоги, квесты, редакторы | Реализованы в переходном API. Квесты сохраняются на уровне мира (`QuestJournal`), поэтому отдельное состояние игроков требует нового контракта. `/storyedit` и `/storyblocks` уже существуют, но нуждаются в развитии. |
| Перезагрузка отдельного файла | `/script reload <файл>` уже реализована. |
| Сохранение и защита одноразовых действий | Сценарии и квесты сохраняются. Для `give_item` есть квитанции запуска; для рычага — действие с желаемым состоянием. Общей атомарной транзакции между миром, инвентарём и файлом сохранения пока нет. |

## Что стоит принять из концепции

1. **Развести ядро исполнения и игровые адаптеры.** Сначала описать контракт шага: запуск, тик, ожидание, отмена, восстановление, ошибка. Затем переносить по одному виду действий из `ScriptPerformer`, сравнивая старый и новый результат на контрольных сценариях. Удаление `ScriptPerformer` до эквивалентной реализации недопустимо.
2. **Ввести библиотеки персонажей.** Добавить контролируемый `require` только для файлов внутри разрешённого корня сюжетного пакета, с канонизацией пути, обнаружением циклов, ограничением размера и кэшем на одну загрузку. Сейчас `LuaStory.parse` явно выставляет `require`, `package`, `dofile`, `loadfile` в `nil`. Это отдельная задача; включать стандартный загрузчик LuaJ нельзя.
3. **Разделить описание NPC и экземпляр.** Текущий `npc{...}` оставить совместимым. Новый шаблон должен быть неизменяемым, а `create_instance` выдавать уникальный ключ экземпляра. Нужно определить, как старые ключи NPC и сохранённые шаги соотносятся с новыми экземплярами.
4. **Уточнить сохранения.** До добавления режимов `temporary`, `world`, `persistent` задать владельца состояния (мир или игрок), ключ персонажа, измерение, поведение при выгрузке чанка и миграцию NBT. Не считать эти режимы уже реализованными.
5. **Версионировать контракт Lua.** Версии движка, API и пакета действительно разные вещи. Начать с манифеста пакета и диагностической команды; прежние файлы без версии трактовать как API 1. Предлагаемый `api_version("2.0")` пока пример, а не существующая функция.
6. **Сохранить простой сценарный синтаксис.** `story`, `part`, `speech` и существующие NPC-команды должны работать во время постепенного добавления API 2.0. Конвертер имеет смысл после фиксации обеих спецификаций; произвольный Lua нельзя надёжно преобразовать простым поиском текста, а промежуточное представление нужно ограничить поддерживаемым подмножеством.

## Важные уточнения к документу

- `parallel(function() ... end, ...)` нельзя просто передать текущему загрузчику. Lua сейчас выполняется при разборе файла и строит последовательность шагов; параллельность потребует отдельного представления веток, идентификаторов действий, правил отмены и восстановления. Сначала нужен контракт исполнителя и конфликтов за NPC/камеру.
- Player API стоит проектировать как отдельную роль, но конкретные `player:say`/`player:think` пока не обещать: есть работающий `think`, а диалог, управление игроком и сетевые права требуют разного поведения.
- Сохранение NPC после перезахода в активном сценарии уже есть. Постоянное сюжетное состояние персонажа между независимыми сценами — другая задача.
- В `gradle.properties` стоит `mod_license=All Rights Reserved`; корневой `LICENSE.txt` описывает Forge/MCP, а не лицензию исходников Storytelling. До смены лицензии нужен отдельный учёт происхождения кода, ресурсов и зависимостей. Этот документ не устанавливает права на них.
- Проверка `gradlew build` не заменяет игру: визуальные экраны, камера, движение NPC и восстановление после перезахода требуют отдельных игровых проверок.

## Практический порядок следующей работы

1. Довести проверку `900050.lua` в игре: выбор и восстановление, квест, предмет без дубля, NPC, камера, завершение. Зафиксировать результат в `integration-chapter-test.md`.
2. Составить таблицу происхождения и активного использования оставшихся Java-классов и ресурсов, не удаляя то, что может быть нужно старым мирам.
3. Формализовать формат сюжетного пакета и контракт безопасного импорта модулей; затем реализовать `require` с тестами изоляции путей и циклического импорта.
4. На этом основании добавить NPC Template/Instance совместимо с `npc{...}` и определить политику долговременного состояния.
5. Описать интерфейс нового исполнителя, эталонные сценарии и миграцию сохранений. Переносить механизмы по частям, включая параллельность после последовательного исполнения.
6. После стабилизации контрактов расширять Player API, редакторы и разрабатывать конвертер для явно поддерживаемого подмножества Lua.

Каждый пункт реализации ведётся в отдельной ветке. До успешной сборки и соответствующих игровых проверок новые возможности не отмечаются как готовые.
