# Основа сюжетного движка: план

Цель: писать главы в `ST/scripts/` на Lua, менять их без пересборки JAR и безопасно продолжать игру после перезахода. Сюжетные файлы и ресурсы должны жить отдельно от Java-кода движка. Этот документ описывает следующую работу, а не обещает уже готовые вызовы.

## Уже работает

Загрузка и `/script reload`, реплики и история чата, ожидания F8/чата/позиции, якоря, сохранение шага, обычные и glTF-NPC, путь NPC, анимации, размер хитбокса и портрет из `Head`. См. [текущий Lua API](story-packs.md) и [ограничения переноса](lua-porting.md).

## Порядок разработки

1. **Зафиксировать контракт сценария.** Описать обязательные `story(id)`, `part("main")`, уникальные имена якорей и NPC, допустимые диапазоны аргументов, ошибки с именем файла и строкой. Добавить команду проверки всех Lua-файлов без запуска мира. Неверный файл не должен ломать загрузку остальных.
2. **Развести загрузку и исполнение.** Lua при загрузке только строит проверяемую последовательность действий. Взаимодействие с миром выполняется на серверном тике через единый реестр действий. Каждому действию задать стабильный тип, аргументы, состояние ожидания и правило восстановления.
3. **Довести сохранение.** Хранить ID сценария, якорь, индекс действия, ожидаемое событие, значения переменных и состояние NPC. После перезапуска продолжать с того же действия без повторной выдачи предметов, реплик или создания NPC. При обновлении Lua-файла обнаруживать несовместимость сохранённого шага и объяснять её в логе/команде.
4. **Добавить переменные и условия времени исполнения.** `var_get/set`, флаги, сравнения и ветвление должны вычисляться во время игры. Нужны локальные для сценария и сохранённые для мира/игрока значения; обычный Lua `if` при чтении файла не заменяет сюжетную развилку.
5. **Диалог с выбором.** Узлы реплик, варианты ответа, условия видимости вариантов, результат выбора и переход к якорю. Историю чата хранить независимо от списка активных сценариев. Проверить повторный вход на экране выбора.
6. **NPC как часть сценария.** Декларации и жизненный цикл NPC, движение с таймаутом и обработкой недоступного пути, взаимодействие, взгляд, анимация, портрет и удаление. Уточнить поведение, когда нужный чанк выгружен или NPC погиб.
7. **Игровые действия.** Предметы, блоки, звук, камера, частицы, экранные эффекты и квестовые операции. Для каждого действия заранее определить серверную/клиентскую сторону и защиту от повторного выполнения после сохранения.
8. **Инструменты автора.** `/script list`, `/script validate`, `/script start`, `/script goto`, `/script stop`, `/script reload`, вывод текущего шага и причины ожидания. Пример одной полной главы и краткая справка по каждому вызову с аргументами и рабочим примером.

## Контрольный сценарий

В отдельном тестовом мире пройти главу: загрузка Lua → появление NPC → реплика с портретом → выбор ответа → перемещение NPC → изменение флага → выход и повторный вход посреди ожидания → завершение. Проверить, что состояние не дублируется, история чата остаётся, а `/script reload` подхватывает новый файл для следующего запуска. Такой сценарий станет проверкой каждого изменения API.

## Первый следующий шаг

Начать с пунктов 1–3: валидатор, единый контракт действий и чёткие правила восстановления. После этого добавлять выбор и переменные: их иначе пришлось бы переписывать вместе с сохранением.
