# Параллельные ветки Lua-сценария

Статус: проектный контракт после `alpha.88`. Публичный Lua API параллельных веток ещё не включён.

## Причина отдельной реализации

`ScriptInstance` уже содержит `PARALLEL_PERFORMERS`, но сохраняет Lua-исполнение через `LuaScriptInstance.mainFlow`. Карта старых параллельных исполнителей не имеет собственного сохраняемого состояния. Подключение к ней Lua-веток привело бы к потере их шага при выходе из мира. Новые ветки должны входить в тот же снимок запуска, что и основной поток.

## Контракт

- Ветка имеет уникальный в пределах сценария постоянный ключ. Снимок хранит ключ, индекс шага, версию состояния активного действия и статус `running`, `done` или `cancelled`.
- Основной поток запускает ветки и ждёт их в точке соединения. Первый режим соединения — `all`: продолжение возможно после завершения всех перечисленных веток. Повторный запуск уже запущенного ключа выдаёт ошибку.
- За один тик ветки исполняются в стабильном порядке по объявлению. Событие чата или F8 получает только ветка, явно ожидающая это событие; при нескольких ожидающих ветках нужен отдельный адресат, иначе запуск отклоняется.
- Камера имеет одного владельца на весь сценарий. NPC имеет одного владельца движения и поворота на каждый ключ NPC. Попытка второй ветки занять ресурс выдаёт ошибку с именами обеих веток и освобождает уже начатые действия новой ветки.
- Выход из мира сохраняет все ветки до освобождения временной камеры и навигации. После входа каждая ветка восстанавливает своё действие по тому же правилу, что основной поток. Завершение или отмена сценария вызывает отмену действий всех веток.
- Переход основного потока к якорю отменяет ветки, запущенные в пропускаемой области. Ветка не может самостоятельно менять индекс основного потока; результат передаётся через переменные с явной областью `scene`.

## Порядок реализации

1. Добавить сериализуемый список веток в `LuaScriptInstance` и тест сохранения двух ожиданий на разных индексах.
2. Ввести запуск и соединение веток только для `wait_ticks` и чистых проверок состояния. Проверить восстановление после перезахода.
3. Добавить адресацию событий и запрет неоднозначного ожидания F8/чата.
4. Добавить владение NPC и камерой, отмену и диагностику конфликтов. Проверить выход в меню во время движения и камеры.

До выполнения этих этапов существующие `part(...)` остаются последовательными частями одного потока.
